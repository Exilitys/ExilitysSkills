# The root file - what actually goes in it

The always-loaded file is the one document every session pays for, so it is the
one most worth being strict about. It is also the one people fill with a
condensed architecture summary, which is the single most reliable way to
produce a doc that lies: two summaries of one subject drift, and the
always-loaded one wins by default while being the more out of date.

## The one rule

> **Every section is a pointer or a rule. Never a summary.**

A *pointer* says where truth lives and stops. A *rule* says what must hold and
cannot be derived from reading the code. A *summary* restates something a
longer document already owns - it is the only one of the three that can go
stale without anyone touching it, because its source moved and it did not.

Apply it per section, not per file. Most drafts fail on two or three sections
and are fine everywhere else.

## Section order

Identity, then where to look, then how to work, then how to check, then what
not to do. Sections a project has no answer for are omitted, not stubbed.

| # | Section | Is it a pointer or a rule | Cap |
|---|---|---|---|
| 1 | What this project is | rule (the framing that is not in any file) | ~15 lines |
| 2 | **Where truth lives** | pointer table - **the reason the file exists** | one row per concern |
| 3 | How work happens - lanes | rule | a table |
| 4 | The gate + contract paths | rule | the literal list |
| 5 | Skills this workflow assumes | pointer | steps the lanes name |
| 6 | Searching this codebase | pointer | ~8 lines, omit if no index |
| 7 | Verification commands | pointer, literal and runnable | the commands |
| 8 | Non-negotiables | rule | **the 3 broken most**, link the rest |
| 9 | Testing strategy | rule - *optional* | what is tested at which seam, and what is **deliberately not** |
| 10 | Out of scope | rule | a sentence |
| 11 | Known highest risk | rule | a paragraph |

If the file runs past roughly 200 lines, section 1 or 8 has started
summarizing. Those are the two that grow.

### 1 - What this project is

The framing a new session cannot reconstruct by reading files: what it does,
the one structural idea that explains the rest, and the stack as a single line.

The test: if the paragraph could be regenerated by skimming the repo for ten
minutes, it is a summary. What survives is the *why* - the decision that
explains the shape, not the shape itself.

### 2 - Where truth lives

A table of **concern -> the one file that owns it**. This is the file's whole
job; everything else is support.

It works because it is falsifiable. Every path in it either exists or does not,
which is what makes the integrity test in `assets/tests/` possible. Prose
cannot be checked; a table of paths can.

One concern, one home. The moment two rows point at the same subject, the next
session gets to pick which to believe, and it will pick wrong roughly half the
time.

### 3 and 4 - Lanes and the gate

The lane table, then the gate with the **literal contract path list** written
out. Do not link the list from here - a session skimming needs to see it
without a second read, and the whole point of the gate is that it stops someone
who is moving fast.

Say plainly that it is membership in a list, not a judgment about importance.
People argue with the list when they think it ranks things.

### 7 - Verification commands

Literal, runnable, copy-pasteable. Not "run the test suite" - the actual line,
with the directory it runs in.

Mark anything advisory as advisory, and say what would make it a gate. An
advisory check that reads as required gets ignored once, then always.

### 8 - Non-negotiables

Name the two or three that get broken most and link the full list. A file of
fifteen equally-weighted rules is a file where none of them are the important
one.

Every rule here must fail loudly when broken. If nothing fails, it is a
preference; move it to the directory-local `AGENTS.md` or write the check.

### 9 - Testing strategy, when it earns a section

Only the part that reading the tests cannot tell you. What *is* covered is
visible in the test directory; what was **deliberately left uncovered, and
why**, is not, and every few months someone proposes adding it back.

Name the most important seam by its literal path. One line each for the tiers,
pointing at the directory-local `AGENTS.md` that owns the detail.

Skip the section entirely if the project has no deliberate exclusions - an
empty ruling is worse than none, because it implies one was made.

## The trim test

Run down the finished file and ask each section one question:

**Does a longer document already own this?**

- Yes, and this restates it -> cut to a link.
- Yes, but this adds a rule the longer doc lacks -> keep only the rule.
- No -> keep it, and it belongs here.

Then ask the whole file: **what in here could become false without anyone
editing this file?** Everything that could, is a summary wearing a rule's
clothes. That question finds in one pass what six months of drift finds
slowly.

## Sections that should not be here

Each of these is a real thing people put in the always-loaded file, and each
has a better home:

| Tempting section | Why it fails | Where it goes |
|---|---|---|
| Condensed architecture | Two summaries diverge; this one wins and is staler | link `docs/architecture/` |
| Component or API listing | The directory cannot go stale; the listing can | the code is the gallery |
| Status / progress / current sprint | Stale by the second session | a `SessionStart` hook, computed |
| Coding standards | Loads React rules into Python sessions | directory-local `AGENTS.md` |
| Style rules a linter checks | A second home for a rule that has config | name the command |
| Changelog or recent work | Git owns this and is never wrong about it | `git log` |
| Aspirational rules | A rule nobody follows teaches that rules are optional | delete, or enforce it |

## Worked skeleton

Genericized from a repo running this system. Prose trimmed to show shape.

```markdown
# CLAUDE.md

Guidance for Claude Code in this repository. **This file routes; it does not
duplicate.** Where a longer document owns a subject, this file names it and
stops - two summaries of one thing drift.

## Project Overview

<What it does, in two sentences. The one structural idea that explains the
rest. Stack as a single line.>

## Where truth lives

| Concern | Lives in |
|---|---|
| Domain vocabulary | `CONTEXT.md` |
| What we are building and why | `docs/prd/prd.md` |
| **What must stay true + contract paths** | **`docs/architecture/invariants.md`** |
| How the system is structured | `docs/architecture/` |
| How backend code is written | `backend/AGENTS.md` |
| How frontend code is written | `frontend/AGENTS.md` |
| What is next / what was deferred | `docs/backlog.md` |

## How work happens here

| Lane | Trigger | Flow |
|---|---|---|
| **1 - Slice** | new user-visible capability | brainstorm -> contract check -> spec -> *(gate)* -> plan -> build -> verify -> review -> PR -> sync |
| **2 - Bug** | wrong behavior | reproduce **first** -> root cause -> failing test -> minimal fix |
| **3 - Chore** | refactor, rename, bump | no spec; **existing tests pass unchanged** |
| **4 - Spike** | "will this even work" | throwaway, not merged |

### The gate

Before editing, check the path against this list:

<the literal paths, written out>

- **Touches one -> STOP.** Spec, approval, then build.
- **Touches none ->** proceed in one session.

Membership in a list, not a judgment about importance.

## Skills this workflow assumes

<the manifest table - see bootstrap.md>

## Verification commands

Run these, and read the output, before claiming anything works.

<the literal commands, with directories>

## Non-negotiables

Full list: `docs/architecture/invariants.md`. The three broken most:

1. <the one that costs most when broken>
2. <the one a tool cannot catch>
3. <the one new sessions get wrong>

## Testing strategy

<what is tested at which seam; the most important seam by path; and what is
**not** tested automatically, so nobody re-proposes it>

## Out of scope (current phase)

<one sentence, so a session stops proposing them>

## Known highest risk

<the part most likely to fail, and what guards it>
```

## Writing it for an existing repo

Do not draft this from the template and then check it against the repo. Draft
it from the repo.

1. Fill section 2 first, from the inventory in `bootstrap.md` step 1. If a
   concern has no home, that is a gap to confirm with the user - not a file to
   invent.
2. Sections 3-5 come from the lanes and the preflight, which are decisions, not
   discoveries.
3. Sections 7-10 come from asking the user. A session cannot derive what is out
   of scope, and guessing produces a rule that gets ignored.
4. Run the integrity test. It will fail the first time; that failure is the
   point.
